# 反合理化參考

## 通用（所有 plan-* Skill 適用）

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| G1 | 「先跳過這步，之後再補」 | 之後不會補。每個跳過的步驟都是下游的隱性債務。 |
| G2 | 「使用者趕時間，精簡一下」 | 使用者沒說精簡。精簡 = 品質下降 = 之後花更多時間修。 |
| G3 | 「這太簡單不需要完整流程」 | 簡單的事會變複雜。流程保護的是未來，不是現在。 |
| G4 | 「把欄位清單／方法簽章／DDL 抄進 plan.md，讀的人比較方便」 | 抄寫是 Token 昂貴與文件漂移的**共同根因**：程式碼一改，抄本立刻變成謊話，而且沒有任何檢查抓得到。「是什麼」一律用 `@code:path#symbol`、`@sql:deploy.sql#table` 錨點指過去；plan.md 只寫程式碼裡看不到的東西（需求、決策與理由、被否決方案、驗收條件、取捨）。 |
| G5 | 「plan.md 要改的地方很多，整檔重寫一次比較整齊」 | 骨架只在 `/plan-start` 用 Write 建立一次，之後一律 Edit 對錨點註解插入。整檔改寫（或把整個章節當 `old_string`）會**靜默吃掉**同一節裡其他階段寫的條目——lint 與測試都不會抓到，因為它們只驗自己關心的維度。 |
| G6 | 「舊決策已經不成立了，直接刪掉那條比較乾淨」 | 決策史正是這份文件唯一不會過期的價值：下一個人要知道「為什麼不走 A」，否則會把被否決的方案再提一次。改變主意用 supersede（`- D-7 [arch] 取代 D-3：…（原因：…）`），共享章節 append-only、以條目為單位。 |
| G7 | 「順手把階段／分支寫進 plan.md frontmatter，之後好查」 | 流程狀態的唯一權威是 `state.json`，唯一寫者是 `crew-state.py`。手寫一份副本＝製造第二個事實來源，兩邊一分歧就沒人知道該信誰。frontmatter 只留身分（`slug`／`name`／`type`）與漂移（`verified_at_commit`／`verified_at`／`drift_policy`）兩類欄位。 |

## plan-build 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| B1 | 「plan.md 的決策紀錄沒有 `[arch]` 條目，我先自己補一條再繼續 build」 | arch pass 未完成是 hard block（`state.json` 的 `steps.arch` 既非 `done` 也非 `skipped`）。自動補寫的架構決策沒有經過使用者審閱，錯誤的分層與介面判斷會傳遞給所有 Teammate，錯誤被放大 5 倍。載體從 arch.md 換成 plan.md 的決策紀錄，這條門檻沒有變鬆。 |
| B2 | 「只有 3 個檔案要改，多角色委派太重了，我就忽略角色契約直接亂寫」 | 角色契約不能省。Host 有 worker 時用 `delegate_write` 隔離；Host 降級 inline 時也必須逐一 role 執行、守 allowed scope 與驗證，不能把降級當成取消規格。 |
| B3 | 「plan.md 有點長，我只讀『指路』節的錨點就好」 | 「指路」只說程式碼在哪，「目標與範圍」「驗收條件」說做什麼、「決策紀錄」說為什麼這樣做。跳過後兩者意味著 Teammate 不知道業務規則、驗證邏輯、錯誤處理策略，產出的 Service Impl 會全是空 TODO。plan.md 全檔 ≤100 行，沒有「太長」這回事。 |
| B4 | 「掃描現有範本太慢，我直接根據技術棧定義產生」 | 技術棧定義只有框架和 ORM 類型，沒有 package 結構、import 順序、annotation 風格、命名慣例。跳過範本掃描的產出需要大量手動修正。 |
| B5 | 「Teammate prompt 已經夠長了，不需要再塞技術棧定義」 | 沒有技術棧定義的 Teammate 會用 Spring Boot 的預設風格，對 Spring MVC 4.x 專案會產出完全錯誤的程式碼（annotation 不同、配置方式不同）。 |
| B6 | 「產完程式碼不用往 plan.md『指路』節補錨點，`git diff` 看得到改了哪些檔」 | `git diff` 只說「動了哪些檔」，不說「哪條決策落在哪個符號」。沒有錨點：`/plan-drift` 無從偵測漂移（等於這份文件永遠不會被驗）、`/plan-review` 不知道該拿哪條決策對照哪段程式碼。補錨點是產碼的一部分，不是紀錄。 |
| B7 | 「DB MCP 查詢太慢，跳過 DB 工程師直接讓後端開始」 | DB 工程師驗證表結構一致性。跳過意味著後端工程師可能依據過期的 `deploy.sql` 或想像中的表結構產生 Entity，欄位名/型別與實際 DB 不符。 |
| B8 | 「退出驗證太嚴格，這次先跳過」 | 退出驗證是防止假完成的最後防線。跳過意味著 plan-review 和 plan-verify 要處理本該在 build 階段就擋住的問題。 |

## plan-review 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| R1 | 「程式碼很簡單，用 --quick 就好」 | --quick 只有邏輯審查，沒有品質和效能軸。簡單的程式碼最容易有 N+1 查詢和不一致的風格。 |
| R2 | 「交叉審查沒新發現，跳過合併步驟」 | 合併步驟不只是匯總，還要去重和排優先級。跳過會讓報告充斥重複問題，也算不出寫進 plan.md「檢查報告摘要」那一條的 🔴/🟡 筆數。 |
| R3 | 「`state.json` 的 `results.verify` 是 FAIL，但那是環境問題，不需要在 review 中提」 | Reviewer 應該判斷 FAIL 是程式碼問題還是環境問題，不是 Leader。把判斷責任留給 Reviewer，前一輪的驗證細節在 `.spec/{slug}/.cache/` 裡，要判斷就去讀。 |

## plan-verify 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| V1 | 「API 回傳 200 就算 PASS」 | HTTP 200 只代表沒有伺服器錯誤。用 curl 檢查回應 body 的格式、筆數、欄位完整性。 |
| V2 | 「snapshot 太長了，我只看前幾行」 | 用 `$B snapshot -D` 看 diff 而不是全文。diff 會高亮變化，不需要掃描整個 snapshot。 |
| V3 | 「這條驗收條件需要登入，太複雜了，標 SKIP」 | 用 `$B connect` 連接已登入的 Chrome，或 `$B cookie-import` 匯入 cookie。gstack 支援 CDP 模式，不需要重新登入。 |
| V4 | 「gstack browse 沒裝，改用 curl 手動測就好」 | curl 只能測 API，無法測 UI 互動、表單驗證、回應式。plan-verify 的核心價值是端到端驗證。 |
| V5 | 「Health Score 太低但功能有跑起來，算 PASS 吧」 | Health Score 是客觀指標。低分代表使用者體驗有問題。記錄實際分數，讓使用者決定是否接受。 |

## plan-security 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| S1 | 「這只是內部 API，不需要安全掃描」 | 內部 API 被 SSRF 攻擊時跟外部 API 一樣危險。而且「內部」定義會隨時間改變。 |
| S2 | 「這個 ${} 是用在 ORDER BY，不能用 #{}」 | 正確，但需要 allowlist 驗證。不是「不能用 #{}」就代表「可以用 ${}」，還有第三條路。 |
| S3 | 「專案已經有 ESAPI，安全應該 OK」 | ESAPI 存在不代表正確使用。最常見的問題是新程式碼忘記呼叫 ESAPI 方法。 |
| S4 | 「掃描結果太多 false positive，沒什麼用」 | Layer 1 是機械掃描，確實有 false positive。但 Layer 2 和 3 是上下文感知的，不能因為 Layer 1 有雜訊就跳過全部。 |

## plan-demo 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| D1 | 「demo 是本地展示，目錄名不用加 `demo-` 前綴也看得出來」 | 前綴是 demo 產物的唯一辨識標記。沒有它，`/plan-status`、`/plan-next`、SessionStart 開場提醒都會把 demo 和真實任務混在一起，使用者評估完後找不到自己真正的任務。 |
| D2 | 「用使用者現有真實任務的 plan.md 當範例比較真實」 | plan-demo 只能用內建假想範例。混用真實任務資料會外洩使用者業務邏輯，且範例引用的 Notion/DB 資料與 `@code:` 錨點在未連線／不同 repo 的環境下並不存在。 |
| D3 | 「demo 反正不寫 Notion，順手跑一下多角色委派讓範例更完整」 | plan-demo 存在的意義就是「零依賴」。一旦呼叫多角色委派或 DB 工具，就違反「5 分鐘無設定體驗」的核心承諾。 |
| D4 | 「.spec/demo-{slug}/ 已存在，直接覆寫沒差」 | 使用者可能保留舊 demo 做對照，必須先詢問是否覆寫，不能預設覆寫掉既有產物。 |

## plan-deploy-confirm 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| DC1 | 「DBA 說都執行成功了，不用逐筆確認，直接全部標記完成」 | 沒有明確帶 `--all-done` 旗標時仍須逐筆詢問，避免漏勾實際失敗或跳過的 Step。 |
| DC2 | 「Notion 沒有『🚀 部署狀態』區塊，我自己在別的地方寫一段」 | 應提示使用者該任務尚未走過標準流程，不能在錯誤位置塞資料，否則下次掃描抓不到這筆回報。 |
| DC3 | 「回滾 SQL 沒有人填，跳過不記錄」 | 至少要記錄「未提供回滾 SQL」，留白會讓下次查核誤以為忘記填而非本來就沒有。 |
| DC4 | 「找不到 deploy.sql，我就當作沒有要回報，安靜略過」 | 應先檢查任務是否走過 `/plan-close`，沒有的話要提示使用者，而不是不聲不響地跳過。 |

## plan-next 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| N1 | 「看一下 `.spec/{slug}/` 有哪些檔案就知道做到哪了」 | 流程位置的唯一權威是 `state.json`，答案一律由 `crew-state.py next` 給。用檔案存在反推是舊版做法，會誤判：驗證跑完但全部 FAIL 一樣有產出檔，照樣推薦「結案」。狀態檔缺失就跑 `crew-state.py rebuild`（結果會標 `inferred`），不是退回用猜的。 |
| N2 | 「使用者一直問下一步很煩，乾脆推薦 /plan-close 讓他滿意」 | 必須照 script 回傳的 `command` / `reason` 轉述，不能為了讓使用者滿意而改寫建議或另給討好答案。 |
| N3 | 「有多個活躍任務，先推薦看起來最重要的那個就好」 | 未指定 slug 且非 `--all` 時要列出全部讓使用者選擇，不能自行篩選只回一個。 |
| N4 | 「`state.json` 說 build 做完了但根本沒有程式碼變更，我幫它改成正確的狀態」 | `crew-state.py` 是 `state.json` 的唯一寫者，而「哪邊才是對的」是使用者的判斷。矛盾時要問：跑 `rebuild` 自我修復，還是照現況續行。自行改寫狀態＝把偵測到的問題掩蓋掉。 |

## plan-drift 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| DR1 | 「符號找不到了，跑個 `--fix` 或直接把錨點改指到最像的那個函式，檢查就綠了」 | `--fix` 只處理 `autofixable: true` 的機械型（`git -M` 改名、行號位移）。**符號消失常代表決策變了**——該動的是「決策紀錄」（用 `D-n [階段] 取代 D-m：…` supersede），不是把指標硬改成能通過檢查。硬改指標會讓文件變成「永遠通過但沒人信」的裝飾，比漂移更糟。語意型一律逐條問使用者。 |
| DR2 | 「這份 plan.md 漂移一堆，改 `drift_policy: off` 最快」 | `off` 不是「修好了」，是「此後完全不檢查」。script 會在總結明示未檢查份數，把它回報成「全部通過」是假資訊。逃生閥由**使用者**決定是否啟用，且優先用行內 `<!-- drift-ignore: D2 reason=… -->`（範圍最小、留得下原因）。 |
| DR3 | 「exit 3 也是非 0，就當有漂移／或當作沒事跳過吧」 | exit 3 是**環境問題**（非 git 工作區、`verified_at_commit` 不在歷史、檔案讀不到），意思是「這次沒檢查成」。說成「有漂移」與說成「檢查通過」都是編造結果。照登 script 的「修法：」原文，並且不蓋章。 |
| DR4 | 「exit 0，那就蓋章 `verified_at_commit` 收工」 | 走哪一步要看 JSON 內容不是只看 exit code——INFO 級的 D3 行號位移不影響 exit code。而且剛改完程式碼就蓋章等於自己給自己蓋合格章：蓋章是承諾，前提是這一輪真的檢查乾淨。 |
| DR5 | 「`--fix` 跑完了，直接照 script 說會修的項目回報」 | `.spec/` 預設被 gitignore，`git diff` 是空的。要用 `--fix` 前後的 `diff` 取回實際改動；**沒出現在 `diff` 輸出裡的就不准說已修好**。 |

## plan-close 專用

| # | AI 的內心獨白 | 為什麼不行 |
|---|-------------|-----------|
| C1 | 「漂移檢查沒過，但程式碼是對的，先結案再說」 | 漂移檢查是結案的硬關卡。沒過就結案＝把一份已知說謊的文件蓋上「已驗證」印章同步到 Notion，之後所有讀它的人都會被誤導。先修錨點或改決策紀錄，再結案。 |
| C2 | 「驗收條件還有兩條沒勾，但功能其實有做，我直接勾起來」 | `AC-n` 的勾選要有本次的驗證證據（`state.json` 的 `results` 或 `.cache/` 的報告）。沒證據就勾＝虛報完成，而且會讓 `/plan-deploy-confirm` 與後續維護者以為這兩條驗過。 |
| C3 | 「結案摘要要寫的東西不少，整份 plan.md 重新排版一次比較好看」 | 結案一樣是 Edit 對錨點插入條目。整檔改寫會吃掉 spec／db／arch／build 各階段寫的決策條目，而這些正是這份文件唯一不會過期的價值。 |
| C4 | 「這功能才改兩行，security／verify／review 我直接標 skipped 就好」 | 快速結案的判定權在人。Agent 只能列出未完成步驟與跳過代價，由使用者明確同意後才 `--by human` 標 skipped；而且跳過的只是檢查，Human UAT 與漂移硬關卡照常執行。自行跳過＝替使用者承擔「沒有安全掃描／驗收／審查證據」的風險。 |
